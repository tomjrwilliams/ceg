  Core data types — at-a-glance

  All of these except Graph and Dependency follow the same shape: a base type with a type: Literal[...] discriminator, a
  per-subclass Snap/Parser companion, and a dump_bytes()/parse_json() round-trip via a tagged-union *Parser produced by an
  lru_cache'd factory (object_parser, event_parser, snap_parser, value_parser, dependency_parser, collection_parser,
  update_parser). The Graph exposes the parser types via event_parser, depends_parser, object_parser, snap_parser, value_parser
  properties — and storage.py reaches them through context.get().<x>_parser to wire serialisers into the KV stores.

  - Object (objects.py:174) — the unit of computation. Frozen dataclass with id: str, parent: str | Object | None, and a
  class-level Snap inner type. Has hooks for depends(), handler(event, snap), and override points for
  event_key_val()/snap_key_val()/value_key_val()/obj_key_val()/dependency_key_val() (see persistence below). get_parent() looks
  up the parent through the current graph in context.
  - Event (events.py:70) — base class for things that flow through the queue: ObjectNew, ObjectChange,
  ValueUpdate/Append/Prepend, and the bootstrap GraphSync. Has obj (path), i (monotonic int per object), t (timestamp).
  Generated by Object.extend_events, which atomically picks the next i and stamps t.
  - Depend(ency) (depends.py:39) — (obj, depends, events, direct). Read as "obj listens to events from depends, of the given
  types." Held in Graph.triggers: depends_path -> {obj_path: Dependency}. The mixins DependsGraphSync, DependsParent{New,Value},
   DependsGrandParentValue, DependsParamsValue, DependsSelf{New,Update,NewUpdate} are the canonical helpers.
  - Handler (objects.py:74) — a stateless object returned by Object.handler(event, snap) whose handle(event, snap, obj) returns
  frozendict[str, (Snap, list[Event])] — i.e. "here are the snaps to set on these (other) objects, and the events to enqueue."
  The handler is what actually mutates state.
  - Snap (snaps.py:65) — per-object running state. Holds handled: {trigger_obj: i} (max event index consumed per upstream), and
  latest: {trigger_obj: t} (for the triage pattern). Optional buffer/updates for batched writes (the SnapUpdates sub-object
  stored at <id>-Updates).
  - Value (values.py:69) — the actual computed payload for an object. Variants: ValueKeyValJSON (small/scalar),
  ValueKeyChunkNumPy/PlSeries (chunked time series), ValueKeyValDf (whole-DataFrame IPC blob). Each storage variant has a
  _SQLite and a _Redis flavour.
  - Graph (objects.py:635) — name, objects: frozendict[id, Object], depends: {id: n_depends}, triggers: {depends_id: {obj_id: 
  Dependency}}. with_obj indexes the object, runs obj.depends(), builds the trigger map, and aliases parent objects to their
  ids. sync() is the scheduler (see below).

  How IDs are built and used

  IDs are dash-joined paths, generated up-front when the object is constructed, then used as the primary key into every backing
  KV. Three layers:

  1. Object.build_id(parent, *segs, strict=False) at objects.py:274 — the only joining primitive. Falsy segments are dropped;
  with no parent it just joins, with a str parent it prefixes "{parent}-", with an Object parent it calls parent.extend_id(...).
   extend_id (objects.py:270) is itself f"{self.id}-{s}".
  2. Per-type .new(...) factories call build_id. Examples:
    - EqDailyEtf.new (etf.py:198): build_id(parent, "eq-etf-d", ident, strict=False) — the segments describe the asset class,
  not the parent prefix.
    - EqDailyRx.new (rx.py:108): parent.extend_id("rx") — derivations just suffix on the parent's id.
    - DailyEM.new (em.py:146): parent.extend_id(params.build_id(cls)) where build_id on the params produces e.g. "ema-4" or
  "ema-0.5-ann-cum". Param-encoding lives on the params object, which is the right place.
  3. init_new (objects.py:126) is a more generic constructor that, when no explicit uid/xid/id is given, uses t.encoder() (a
  frozendict of per-field stringifiers) to deterministically render each kwarg into the id. It's a fallback path the bar/calc
  objects don't actually use — the canonical pattern is bespoke cls.new() factories.

  A few observations:
  - IDs are intended to be content-addressed (same params → same id → same row in storage). The version: int = 0 field on most
  concrete types is presumably the cache-bust knob if the calculation semantics ever change without the params changing — but it
   isn't actually in the id, so changing version won't currently invalidate stored values. Likely gap.
  - Pydantic-serialised parents are encoded as their id string (Object.dump_bytes does replace(parent=self.parent.id) if parent
  is an Object), but in-memory parents are usually the Object itself until with_obj calls alias_parents (objects.py:1432), which
   rewrites every Object-typed field on a frozen dataclass to its .id via obj_type_hints introspection. So inside the graph,
  object fields ultimately store paths, not references. That's important: it's why Dependency.depends and Object.parent look
  like raw strings everywhere in the trigger map.
  - Helpers alias_parents / obj_to_alias walk lists/tuples/dicts/sets but don't recurse into frozendict or arbitrary models
  (objects.py:1412-1429). If you ever embed an Object inside a frozendict field, its alias won't be flattened — silent
  bug-in-waiting.
  
  Persistence per object

  The pattern is: each object decides which KV-store to use for each of its five domains (object, event, dependency, snap,
  value). Default unwiring lives in Object itself (obj_key_val() returns SQLite with TEST_DB), but the production path is the
  UseRootStorage mixin (storage.py:198).
  
  UseRootStorage splits the id on the first - and uses the leading segment (e.g. "test" from "test-eq-etf-d-...") as the storage
   "root", then looks up a StorageConfig object in the current graph keyed config-storage-{root}-{domain}-{mode} (r or w). The
  config is itself a graph-managed Object, so wiring a project happens by:
  
  Project.new("test").set_storage_defaults(roots=["test"], read={"db": REDIS})

  which inserts ~14 StorageConfig objects (7 defaults × {r,w}) into the active graph. storage.event_key_val(config) etc. are
  LRU-cached on the config, so a given (root, domain, mode) triple has one shared backend instance.

  Variants:
  - UseRootChunkedStorage overrides value_key_val to use the chunked Polars-series backend with key
  config-storage-{root}-value-chunked-{mode} (e.g. for DailyChunked).
  - UseRootDataFrameStorage ditto with the IPC-DataFrame backend (config-storage-{root}-value-dataframe-{mode}).
  
  The event store is interesting: there is no single "latest event for object" record and no per-step record — they store both.
  Object.extend_events (objects.py:346):

  e = kv.set(f"{self.id}/{i}", e)   # per-i row
  _ = kv.set(self.id, e)             # latest pointer

  So you can fetch obj.get_event() for the latest or obj.get_event(i) for a specific one. That's two KV writes per event, with
  the same payload — works, but doubles write amplification and storage. Possible optimisation: a single keyed-list/queue type,
  which the commented-out EventKeyChunk block in events.py hints was the previous plan.
  
  Snaps optionally batch via Snap.buffer (snaps.py:200): if set, snap mutations accumulate into a sidecar <id>-Updates row until
   len(updates.handled) >= buffer, then flush. Reads must use Snap.get(key, kv) (the classmethod) to merge updates back in.
  There is one bug in there: merge_updates calls replace(...) without self= as the first arg (snaps.py:144). It will only fire
  on the buffered-read path so it's been hiding; I'd treat it as broken until proven otherwise.

  The dependency graph and how sync() runs

  Graph.with_obj (objects.py:735) does the indexing:

  1. If parent is an Object and not yet in the graph, recursively insert.
  2. obj.check().alias_parents() — convert Object fields to ids.
  3. Save to self.objects.
  4. Call obj.depends(). Each Dependency(obj=self.id, depends=upstream_id, events=...) is added to
  self.triggers[upstream_id][self.id] = dep. self.depends[obj.id] = len(depends) (used by triage later).

  Graph.sync (objects.py:786) is a priority-queue scheduler keyed on event timestamp:

  1. For every object: compare stored Object with the in-memory copy via sync_object_def. If new, emit ObjectNew. If changed
  (via ObjectDiff), emit ObjectChange. Persist the new object.
  2. Push a GraphSync event for the graph itself.
  3. For each object, look at its dependencies. For each upstream, fetch the upstream's latest event from events (or from
  storage). If snap.handled[upstream] < latest.i (or the upstream is GraphSync), push the next un-handled upstream event onto
  the heap.
  4. Drain the heap: for each event, look up self.triggers[e.obj] to find every downstream listener; for each, call handle_event
   which:
    - Calls obj.handler(e, snap).handle(e, snap, obj) → {path: (snap, [events])}.
    - For each path: run extend_events (persists events), set_snap (persists snap), push the new events onto the heap.
    - Marks the listener's snap.handled[upstream] = e.i.
  5. If processing a real event advances its source object, the next event from that source is pushed (objects.py:917-922).

  So the scheduler is correct-by-construction up to the heap ordering: handlers can produce ripple events (via the returned
  {path: (snap, es)}), and those get re-queued. Events are processed in t order, which matters when multiple upstreams fire in
  the same sync.
  
  The triage mechanism (handle_event lines 957-967, TriageUpstream at handlers.py:275) is for downstream objects that wait until
   all upstreams have published once before firing. The condition len(snap.latest) == n_depends[obj.id] - 1 says "when this is
  the last upstream to first-publish, actually run the handler." Subtle, easy to get wrong; I'd want a test specifically
  targeting it.

  Object namespacing with parents

  The "parent" concept does double duty:

  1. ID prefix — parent.extend_id(suffix) builds child ids by string concat. Whole derivation chains
  (test-fut-d-ES-1-close-pct-frd-rx-ema-4) are just nested extends.
  2. Storage root resolution — UseRootStorage.value_key_val() splits on the first - and uses that as the storage namespace. This
   relies on the convention that the first id segment is a Project name (e.g. "test"). It's load-bearing but not enforced
  anywhere.
  3. Logical dependency — parent is also typically what DependsParent* mixins point at. EqDailyRx extends
  DependsEqDailyEtfParent, so the rx automatically declares Dependency(self.id, parent.id, events=("ValueUpdate",)). This is the
   clearest example of parents being structural, not just naming.

  The Project / Config / StorageConfig types live in the same graph as data objects — they're just objects with their own ids.
  Project.set_storage_defaults injects 14 StorageConfigs. They're queried by id, so any object can find its storage config by
  walking up to its project name via the id prefix. Neat, but a little surprising — there is no formal "config registry"; it
  really is just a frozendict in Graph.objects.

  Worth noting: a Project is just a parent for namespacing and storage routing; Config extends UseRootStorage so it'll try to
  look up its own storage (which would be circular). Looks fine in practice because configs are looked up by id directly, never
  .set_obj()-persisted — but the inheritance hierarchy is misleading.

● I've now read collections.py more carefully alongside sign.py and app/core.py. Below is what I think the design is trying to
  be, where the friction is, and concrete suggestions for tightening it up.

  What collections.py is for (as I understand it)

  A Collection is a second registry of objects that sits alongside the Graph, with three things the graph doesn't have:

  1. Aliases — short, human-friendly names ("cv-EQ-SPY") → long auto-generated ids ("states_sign-cv-eq-etf-d-SPY-...-rx-cv").
  The graph is keyed by id; the collection lets you talk in aliases.
  2. Tags + info — {key: frozenset[str]} and {key: frozendict}. The query DSL (where, select) filters on these.
  3. Construction-deferred building blocks — Bound / Bind / Apply are recipes, not objects. They get expanded later: Bind(...)
  iterates a Select, calls a constructor for each combo, and registers the result in the collection (and graph).

  The flow in sign.py is:
  
  AppConfig.with_configs(name=Bind|Apply, …)   # declarative
  → AppConfig.run:
      Phase 1: for each Bind config → bind(collection)
               # this populates both graph.objects and collection.objects
      Phase 2: graph.sync()
      Phase 3: for each Apply config → apply(collection, res)
               # vis / plots / writes

  So Bind is "build this many objects of type X by zipping/producting these inputs, and register under this alias pattern."
  Apply is "after sync, run this output pipeline."

  Where the design rubs

  1. Two parallel registries
  
  Graph.objects: {id → Object} and Collection.objects: {alias → Object} are both authoritative for the same set of objects.
  Bound.bind does context.get().with_obj(...) and collection.with_obj(...). They can drift, the wiring is implicit, and
  consumers downstream of sync have to know which to look in. Practically: alias-only views like c.get("cv-EQ-SPY") and id-only
  views like graph.get(...) are both used in your code.

  2. Stringly-typed references everywhere

  Multiple ad-hoc reference languages stuffed into plain strings:

  - "o:cv-EQ-SPY" — object reference (handled by unpack_bound)
  - "o:cv-EQ-SPY.rx()" — object reference + method call (obj.rx())
  - "data:sign_code" — pipeline data reference (used in Apply.then)
  - "param:rx_s.d0" — parameter reference (also in Apply)
  - Tags like "strats/cv" — slash-segmented namespace
  - {key}/{k} — alias prefixing

  These overlap conceptually but each has its own parser/resolver, none statically checkable, and the failure mode when one is
  wrong is a runtime ValueError deep in unpack_bound. A typed Ref/Tag/Data/Param discriminated union would replace all of these 
  and survive a refactor.
  
  3. Too many overlapping construction mechanisms

  There are now four ways to build an object:
  
  ┌──────────────────────┬──────────────────────────────┬───────────────────────────────────────────┐
  │      Mechanism       │            Where             │                  Used by                  │
  ├──────────────────────┼──────────────────────────────┼───────────────────────────────────────────┤
  │ cls.new(...) factory │ Per-type (EqDailyEtf.new, …) │ Everywhere                                │
  ├──────────────────────┼──────────────────────────────┼───────────────────────────────────────────┤
  │ init_new             │ objects.py:126               │ Nothing in tree right now                 │
  ├──────────────────────┼──────────────────────────────┼───────────────────────────────────────────┤
  │ init_bind → Bound    │ collections.py:436           │ Some, via bind_params                     │
  ├──────────────────────┼──────────────────────────────┼───────────────────────────────────────────┤
  │ Bind                 │ collections.py:822           │ sign.py (select(...).bind(strat.cv, ...)) │
  └──────────────────────┴──────────────────────────────┴───────────────────────────────────────────┘

  They have subtly different rules for parent-handling, default-filling, id-construction, and arg resolution. init_new/init_bind
   look like an earlier attempt at a generic factory that you ended up routing around with bespoke .new() methods and then Bind.
   My read: keep cls.new() as the canonical, delete init_new/init_bind/Bound, and have a single Bind that calls whatever 
  callable you give it.

  4. Bind.__call__ is doing several jobs at once

  In ~80 lines (collections.py:904-980) it:

  - iterates the select
  - merges params
  - unpack-resolves refs (with a force distinction that's not obvious)
  - splits args into positional vs keyword via arg_order
  - pops into_fields for container-mutation
  - calls func
  - if into_fields present, calls .bind(...) on the result with t=type(into) (mixing types and instances)
  - handles mutates_fields returning (mut, mut, ..., res) tuples
  - attaches FUNC/CONFIG to info
  - raises ValueError(self) if zero rows

  The configuration surface (unpack_fields, arg_order, mutates_fields, bind_fields, into_fields) all exist because the call site
   can't easily express what it needs — each knob fixes one historical case. A typed function signature with annotated parameter
   kinds would collapse most of this.
  
  5. Apply / Output.then is a half-baked pipeline DSL

  Output.__call__ (collections.py:1012-1043) handles three positional shapes — first-call-with-collection, last-call-with-acc,
  middle-call-passing-through — and dict-versus-non-dict to pick **res vs positional. The "data:..." / "param:..." strings in
  vis.write_data calls are then resolved … somewhere else (didn't see it here; I assume in vis.write_data). The dataflow between
   stages is implicit and order-dependent.

  6. Concrete bugs I spotted in collections.py

  Worth fixing before refactoring, since they'll mask intent:

  - collections.py:887 — args = ("parent,") + args — note the trailing comma inside the string. Should be ("parent",) + args.
  The current path only works because nothing puts parent in arg_order; the moment something does, the lookup params[a] will
  KeyError on the literal "parent,".
  - collections.py:220 — keys = keys | self.tags.get(key, set()) — should be self.tags.get(t, set()). Will read tags under the
  wrong key (matching object id instead of tag name). Only the single-tag case currently goes through cleanly.
  - collections.py:165-167 — if isinstance(obj, Object) is always true (typed Object param); the conditional is dead.
  - collections.py:561 zip_every_kwargs — z_it = zip(*z.values()) is captured before the itertools.product, so it's a one-shot
  iterator. The product will consume it on the first outer iteration and yield nothing thereafter for any len(every_values) > 1.
  - collections.py:577 — assert not any([k in acc for k in d.keys()]), (ds) — when a Select's output (via .alias(k)) collides
  with Bind.params (e.g. you wrote name=... both in the select and in .bind()), this just blows up with the raw tuple. No path
  explanation.
  - collections.py:413 — assert self.container.startswith("o:"), self — but the only writer to Bound.container (which I can't
  see being set anywhere by init_bind/bind_params) presumably should set it explicitly. Today this branch is unreachable from
  init_bind; Bind.into is the only thing that exercises container mutation.
  - collections.py:740-744 — SelectWhere.generate returns [{name: [Aliased(...), ...]}] (a list of length 1) when group_by is
  the empty tuple, but returns a generator-friendly list when group_by is None. The product of these in SelectProduct.generate
  works, but it's a footgun: changing group() → group("x") switches the cardinality and the consumer doesn't necessarily know.
  - collections.py:903 — if isinstance(self.name, str): return self.name.format(**kw) — but kw has been partially consumed by
  unpack_bound_kw (positional args were popped into args). If your alias template wants {parent}, you'll get a KeyError because
  parent was moved out.

  7. Soft pain points

  - Aliased(name, obj) is essentially "the alias the predicate matched the object under, bring it back." It's only sometimes
  unwrapped (Bind.unpack_aliased). In some places it's there for the consumer to see the alias, elsewhere it's noise. Two
  separate intents in one type.
  - select(...) factory is overloaded — same function name builds SelectLiteral, SelectWhere, SelectProduct, SelectZip depending
   on combinations of every / zip / kwargs / list-values. Reading a call requires knowing the dispatch table.
  - .group() with no args vs .group("x") has very different semantics. Worth two methods.
  - Collection.merge has a # TODO: tags, info — it loses them.
  - tag in with_obj allows nested-namespace tags via "a/b/c" splitting, but where(tag=...) doesn't have the equivalent prefix
  lookup (tags.get(key, set()) does exact match only).

  What I think a cleaner shape looks like

  I'll sketch it as four separable moves; we can pick any subset.

  Move 1 — Fold Collection metadata into Graph
  
  Add aliases, tags, info directly to Graph. Collection either disappears or becomes a thin builder that just calls
  graph.with_obj(..., alias=..., tag=..., info=...). Single registry, no drift, lookup by alias and id are both first-class.
  This is the biggest win and the prerequisite for the rest.
  
  Move 2 — Replace string refs with typed refs

● Container — what it actually is

  Reading agg/{containers,aggs,combs,aggregations}.py in light of the previous two passes, the picture clicks. A Container is a 
  persisted, indexed sub-namespace that lives in the graph as an Object. Specifically it provides four interning tables:

  ┌───────────────────────────────────┬────────────┬───────────────────────────────────────────────────────────────────────┐
  │               Table               │    Type    │                            What it solves                             │
  ├───────────────────────────────────┼────────────┼───────────────────────────────────────────────────────────────────────┤
  │ objects: tuple[Object | str, ...] │ positional │ a stable int handle for an object whose full id is too long to inline │
  ├───────────────────────────────────┼────────────┼───────────────────────────────────────────────────────────────────────┤
  │ agg: tuple[Aggregate, ...]        │ positional │ "this aggregation references container objects [3, 7, 12]"            │
  ├───────────────────────────────────┼────────────┼───────────────────────────────────────────────────────────────────────┤
  │ comb: tuple[Combination, ...]     │ named      │ "this combination is {rx: obj_3, w: agg_2}" — typed kwargs            │
  ├───────────────────────────────────┼────────────┼───────────────────────────────────────────────────────────────────────┤
  │ params: tuple[TParamDict, ...]    │ positional │ parameter dict interning, referenced by integer                       │
  └───────────────────────────────────┴────────────┴───────────────────────────────────────────────────────────────────────┘
  
  with_object / with_agg / with_comb / with_params are all the same shape — append-if-new, return (new_self, idx). They're
  content-addressed via linear scan (find_object etc.) — an O(n) dedup, but the integers it returns are stable handles you can
  put inside the id of a downstream object.

  That's the load-bearing trick: DailyAggregate.new(container, "hsum", aggs=[Aggregate_3]) builds an id like
  <container-id>-agg-3-hsum. The agg's identity is now derivable from (container_id, agg_index), and the container holds the
  actual object list. Three things this gives you:

  1. A stable id for compositions whose member-list is too long to encode literally — your motivating problem.
  2. Triage gating — Container extends TriageUpstream, so it fires one ValueUpdate when all member objects have first published.
   Downstream aggs depend on the container, not the members. Without containers, an agg over 30 series would have 30 deps and
  the trigger logic would be much hairier.
  3. A dynamic-output hook — handlers can return (df, [(key, idx)]), and the handler then spawns DailyAggregateDeriv children
  whose ids are derived from (container, agg, key, idx). Those derivs have depends() == [] because the parent's handler writes
  them directly.

  So we now have three near-overlapping concepts
  
  ┌──────────┬────────────────┬──────────────────┬──────────────────────────┐
  │          │     Graph      │    Collection    │        Container         │
  ├──────────┼────────────────┼──────────────────┼──────────────────────────┤
  │ Key      │ id (full path) │ alias (short)    │ int (positional)         │
  ├──────────┼────────────────┼──────────────────┼──────────────────────────┤
  │ Lifetime │ run-time       │ build-time       │ persisted as Object      │
  ├──────────┼────────────────┼──────────────────┼──────────────────────────┤
  │ Metadata │ none           │ tags, info       │ agg, comb, params        │
  ├──────────┼────────────────┼──────────────────┼──────────────────────────┤
  │ Used by  │ scheduler      │ DSL              │ aggregations             │
  ├──────────┼────────────────┼──────────────────┼──────────────────────────┤
  │ Mutation │ with_obj       │ with_obj (alias) │ with_object (+ idx)      │
  ├──────────┼────────────────┼──────────────────┼──────────────────────────┤
  │ Dedup    │ by id          │ by alias         │ by content (linear scan) │
  └──────────┴────────────────┴──────────────────┴──────────────────────────┘
  
  They are all the same pattern: a Map[Key, Object] with side metadata, plus an add(obj) → (self', key) constructor. The
  differences are key-type, lifetime, and what metadata they happen to carry. The current code treats them as three different
  classes wired together by string conventions, with the Bind machinery in collections.py doing the gluing.

  Rationalised model

  Here's what I think the clean structure looks like, working bottom-up.
  
  Layer 1: Ref — one typed reference family

  Replace every stringly reference ("o:foo", "obj_3", "data:x", "param:y.z") with a small discriminated union:
  
  @dataclass(frozen=True)
  class Ref: ...                      # base, all carry .resolve(ns) -> Object|Any
  class IdRef(Ref):    id: str        # absolute graph id
  class AliasRef(Ref): name: str      # graph alias (was "o:name")
  class IndexRef(Ref): container: Ref; kind: Literal["obj","agg","comb"]; i: int
  class DataRef(Ref):  name: str      # pipeline output (was "data:name")
  class ParamRef(Ref): path: str      # was "param:foo.d0"
  
  unpack_bound becomes ref.resolve(ns). Static-typeable, refactor-safe, no string parsing. Ref is also what gets stored inside
  Combination/Aggregate (instead of the current "obj_3" encoding).

  Layer 2: Namespace — the unified Map[Key, Object]+metadata

  Graph, Collection, and Container are all instances of a common Namespace protocol:
  
  class Namespace(Protocol):
      def with_obj(self, obj, *, key=None, **meta) -> tuple[Self, Key]: ...
      def get(self, ref: Ref) -> Object: ...
      def where(self, **filters) -> Self: ...
  
  Concrete implementations:

  - Graph — root namespace, id-keyed, owns the scheduler. Gains aliases, tags, info fields directly (Collection's current
  contribution).
  - Container — a Namespace and an Object (its own member of the parent Graph). Key is an int index. Holds compositions
  (agg/comb) as further interning tables.
  - Collection — disappears, or becomes a thin build-time wrapper that proxies to a Graph.
  
  The with_obj → (new, key) shape is uniform. Bind always receives that shape and threads new forward — no more mutates_fields.
  
  Layer 3: Composition — one type instead of Aggregate + Combination

  @dataclass(frozen=True)
  class Composition:
      refs: tuple[Ref, ...] | frozendict[str, Ref]   # positional or named
      params: Ref | None = None                       # optional ParamSet ref
      index: int = -1
  
  Today Aggregate is the positional case, Combination the named case, Aggregate.get_objects and Combination.with_objects are
  similar enough to share. Unifying lets you do container.with_composition(...) with one signature and one storage slot.

  Layer 4: Bind consumes only the unified surface

  With layers 1–3, the Bind flow becomes:
  
  graph = (
    bind(strat.cv, asset=symbols)            # cls.new(asset=..., container=ref)
    .under("cv-{asset}")                      # alias template
    .info(asset=...)                          # tag/info
    .into(graph["strats-cv"])                 # if cls.new returns (container', obj), thread automatically
  )
  
  No unpack_fields, no arg_order, no mutates_fields. The function signature is the source of truth: a Ref parameter gets
  resolved against the namespace, a return shape of (Namespace, X) is handled by the Bind machinery. Position vs. keyword is
  whatever the Python function signature says.

  Apply likewise — its current "data:..."/"param:..." DSL becomes DataRef/ParamRef, and the .then(...) stage chain operates on
  those typed refs.
  
  Layer 5: Derivs as first-class fan-out

  DailyAggregateDeriv and DailyCombinationDeriv are the same pattern: a child object whose value is written by a parent's
  handler, no depends() of its own. Turn it into one helper:

  @dataclass(frozen=True)
  class Output(Object):
      parent: Object | str
      key: str | None = None
      index: int | None = None
      # depends() -> []  (data written by parent's handler)

  Then DailyAggregate.deriv(...), DailyCombination.deriv(...), and anything similar all return Output(self, key, index). Both
  aggs.py:325-362 and combs.py:364-400 collapse into one store_child helper on the base handler. This also makes the implicit
  "fan-out" pattern visible — anyone reading the codebase can grep for Output to see all the points where dependencies leave the
   explicit graph.

  Layer 6: Container as a Namespace-aware Object
  
  Keep Container's TriageUpstream role (gate fan-in on all-members-first-fired). But give it the Namespace protocol and let aggs
   reference members via typed Refs rather than int args. The int handles can stay as a render of the Ref for id-building, but
  the API takes Refs.

  What this buys

  - One Ref type to grep / type-check / refactor — eliminates ~five string mini-DSLs.
  - One with_obj → (new, key) shape — eliminates mutates_fields/into_fields from Bind.
  - One Composition type — eliminates the Aggregate/Combination split.
  - One Output type — eliminates Deriv duplication and surfaces the fan-out pattern.
  - Graph directly carries aliases/tags/info → no Collection parallel registry to keep in sync.

  Incremental addition

  Graph is already incrementally additive — with_obj is a frozendict update returning a new Graph, and Bound.bind already calls

  doesn't have. The only thing Collection adds is the extra metadata to track during each add. That metadata can ride on
  with_obj directly:

  def with_obj(
      self,
      obj: Object,
      *,
      alias: str | None = None,
      tag: str | tuple[str, ...] = (),
      info: frozendict | None = None,
      force: bool = False,

  Alias and id in separate maps, both addressable

  @dataclass(frozen=True)
  class Graph:
      objects: frozendict[str, Object]        # id → obj
      aliases: frozendict[str, str]           # alias → id  (session-local)
      # ... other fields

      def get_alias(self, alias: str, t: Type[O] | None = None) -> O: ...

      def get(self, ref: Ref, t: Type[O] | None = None) -> O:
          match ref:

              case AliasRef(name):  return self.get_alias(name, t)
              case IndexRef(container, kind, i):

  Note alias/tag can now apply to a non-Object ref (an agg or comb). Two options:

  a) Only objects get aliases/tags. with_nested_agg ignores those kwargs (or rejects). Aggs are referenced by their IndexRef,

  an agg ref. The internal map just changes from {alias: id} to {alias: Ref}, and get_alias follows the ref through.

  How this composes with Bind

  With the three nested methods on Graph, Bind collapses dramatically. The deferred recipe just needs to know "where to add the
  result." A single target parameter:

  bind(strat.cv, asset=symbols, span=48).into(F.alias == "strats-cv-{asset}")

  The into("strats-cv-{asset}") template is resolved per row to find the right container alias. The

  and that's picked up from the Bind's shape (bind, bind_agg, bind_comb) rather than configuration kwargs.

  @dataclass(frozen=True)
  class Graph:

      name: str | None
      objects: frozendict[str, Object]
      depends: frozendict[str, int]

      def with_tag(self, ref: Ref, tag: str | tuple[str, ...]) -> Graph: ...
      def with_info(self, ref: Ref, info: dict | frozendict) -> Graph: ...

      def get(self, ref: Ref, t: Type[O] | None = None) -> O: ...
      def get_id(self, id: str, t: Type[O] | None = None) -> O: ...
      def get_alias(self, alias: str, t: Type[O] | None = None) -> O: ...

      def where(
          self,

          paths: dict[str, Any] | None = None,    # {"tags.symbol": "SPY"}
          type: Type | tuple[Type, ...] | None = None,

      ) -> Iterator[Object]: ...

  (2) Project ≈ Container — generalise to Namespace

  Squinting at what they actually do:
  
  - Project — top-level, no parent, name-keyed, used to namespace storage routing.
  - Container — has parent (Project), name-keyed, holds indexed members + agg/comb/params interning.
  
  Both are "named Objects that act as namespaces for descendants." The only structural differences:

  1. Project sits at the root (parent: None)
  2. Project routes storage; Container doesn't
  3. Container has indexed members; Project doesn't

  (2) and (3) are capabilities, not type identities. A Project that happens to acquire indexed members would still be a Project.
   So:
  
  @dataclass(frozen=True)
  class Namespace(Object):
      parent: Namespace | str | None
      name: str

      # optional indexed members — for the Container role 
      members: tuple[Object | Ref, ...] = ()

      # optional storage routing — for the Project role
      storage: frozendict[str, str] | None = None   # domain -> conn/table/etc.

      # the with_* methods all live here, return (self', ref)
      def with_member(self, obj) -> tuple[Namespace, IndexRef]: ...

  class Project(Namespace):
      parent: None
      # storage required, members usually empty

  class Container(Namespace):
      parent: Namespace
      # members required, storage usually None

  That removes one of the load-bearing string conventions (every id's first segment being the project name).

  - Each DailyComposition is itself a member of the namespace; its refs/named/params are its own fields, not a duplicate
  registry on the namespace.

  (3) Auto-generating ids from parent + slot

  This is the most radical and the most rewarding. Right now you have ~10 id-construction patterns scattered across .new()
  factories. They all decompose into:
  
  id = parent.id + "-" + role + ("-" + params_encoded)?

  Where role and params_encoded are per-type. If we lift that uniform shape out:

  @dataclass(frozen=True) 
  class Object:
      @classmethod
      def role(cls, **fields) -> str:
          """Default: class name → kebab-case. Override for symbol-prefixed ids etc."""
          return camel_to_kebab(cls.__name__)

      @classmethod
      def encode_params(cls, **fields) -> str:
          """Default: empty. Override per type with whatever encoding (DailyEMParams etc.)."""
          return ""

      @classmethod
      def auto_id(cls, parent, **fields) -> str:
          role   = cls.role(**fields)
          params = cls.encode_params(**fields)
          suffix = role + (("-" + params) if params else "") 
          return parent.extend_id(suffix) if parent else suffix

  Then every .new() becomes:
  
  @classmethod
  def new(cls, parent, **fields):
      return cls(id=cls.auto_id(parent, **fields), parent=parent, **fields)

  A truly minimal type doesn't need to override anything (role defaults to class name, no params encoded). DailyEMA overrides
  encode_params to produce "4" or "0.5-ann-cum". EqDailyEtf overrides role to produce "eq-etf-d-SPY". Etc.
  
  Where this combines beautifully with with_nested_*:

  For positional members of a Namespace, the slot is i:
  
  graph, ref = graph.with_member(container, obj)
  # obj.id auto-generated as `<container.id>-<obj.role()>-<len(container.members)>`
  # or even just `<container.id>-<i>` if `role` defaults to position

  For named members: 
  
  graph, ref = graph.with_member(container, obj, key="rx")
  # obj.id = `<container.id>-rx`

  This lets the user say:
  
  graph, etf = graph.with_member(project, EqDailyEtf(...), key="SPY-pct-frd")
  # id = "test-SPY-pct-frd" — the field "key" provided the slot

  graph, rx = graph.with_member(etf, EqDailyRx(...), key="rx")
  # id = "test-SPY-pct-frd-rx"
  
  graph, ema = graph.with_member(rx, DailyEMA(...), params={"span": 4})
  # id = "test-SPY-pct-frd-rx-ema-4" — params encoded by type

  The id-construction logic isn't eliminated, but it's reduced to:
  - a) what role/key does this slot have (caller decides),
  - b) how do params encode (one method per type with params).

  Everything else falls out.

● Yes — this is the right generalisation. Let me work through what it actually looks like and where the edge cases land, because
   there's one distinction worth being explicit about up front.

  The clean primitive

  def with_nested(
      self,
      parent: Object | Ref | str,
      field: str,
      child: Object,
      *,
      index: int | None = None,     # for tuple/list slots; None = append
      key: str | None = None,       # for dict slots; required when field is a dict
      alias: str | None = None,
      tag: str | tuple[str, ...] = (),
      info: dict | None = None,
  ) -> tuple[Graph, Ref]:
      parent = self.get(parent, Object)
      current = getattr(parent, field)

      if isinstance(current, (tuple, list)):
          slot = str(len(current) if index is None else index)
      elif isinstance(current, (dict, frozendict)):
          assert key is not None, (parent, field, child)
          slot = key
      else:
          raise ValueError(parent, field, type(current))

      # 1. derive child id from parent + field + slot
      child_id = parent.extend_id(f"{field}-{slot}")
      child = replace(child, id=child_id, parent=parent.id)
  
      # 2. write parent's field with the new child reference
      if isinstance(current, (tuple, list)):
          if index is None or index == len(current):
              new_field = (*current, child_id)
          else:
              new_field = (*current[:index], child_id, *current[index+1:])
      else:
          new_field = (current.set(key, child_id)
                       if isinstance(current, frozendict)
                       else {**current, key: child_id})
      parent = replace(parent, **{field: new_field})

      # 3. add both to graph (this also re-runs parent.depends() and updates triggers)
      self = self.with_obj(child, alias=alias, tag=tag, info=info)
      self = self.with_obj(parent, force=True)
      return self, IdRef(child_id)

  This handles Container.with_object(obj), Container.with_agg(refs), Container.with_comb(**refs) — they're all
  graph.with_nested(container, "objects"|"agg"|"comb", thing). Container the type doesn't need to exist anymore; any Object with
   a tuple-of-refs or dict-of-refs field works identically.
  
  The distinction that actually matters

  There are two kinds of "parent" relationships in your codebase, and the consolidation only fully works for one of them:

  Identity-stable parents (containers, projects)
  
  The parent's id is independent of which children it holds. Container("strats-cv") has id "test-strats-cv" whether it contains
  1 member or 50. You can add members incrementally, and the parent's id is stable through that growth.

  with_nested is precisely for these. Adding a child:
  - Doesn't change the parent's id
  - Doesn't change any downstream consumer's view of the parent (they still resolve parent.id → an Object, just one with a
  longer members tuple now)
  - Re-runs parent.depends() to register the new edge with the scheduler (TriageUpstream picks up the new member as an upstream)
  
  This is the case you're describing. Containers, Projects, anything with a "bag of children" slot. They all collapse to "Object
   with a list/dict field + use with_nested."

  Identity-derived parents (data, compositions, calcs)

  The parent's id is a function of its data. EqDailyEtf(symbol="SPY", adjust="pct", source="frd") has id
  "test-eq-etf-d-SPY-close-pct-frd". The data and the id are bound together.

  For these, the children are usually expressed by the child holding parent as a Ref, not by the parent holding a children list.
   EqDailyRx's parent is the etf; the etf doesn't carry an .rx field. The relationship is back-referenced, and id derivation
  runs the other direction: child.id = parent.extend_id(child.role) at child-construction time.
  
  For these you don't need with_nested — plain graph.with_obj(child) with child.parent set is the existing path, and it works
  fine because nothing about the parent needs mutating.

  So the model is two creation idioms, not one:

  ┌───────────────────────────┬───────────────────────────────────────────────────────┬────────────────────────────────────┐
  │                           │                   Forward reference                   │         Backward reference         │
  ├───────────────────────────┼───────────────────────────────────────────────────────┼────────────────────────────────────┤
  │ Slot lives on             │ parent                                                │ child                              │
  ├───────────────────────────┼───────────────────────────────────────────────────────┼────────────────────────────────────┤
  │ Parent id depends on      │ nothing (or its own static fields)                    │ its own data                       │
  ├───────────────────────────┼───────────────────────────────────────────────────────┼────────────────────────────────────┤
  │ Adding a child requires   │ parent                                                │ nothing (just creates child)       │
  │ mutating                  │                                                       │                                    │
  ├───────────────────────────┼───────────────────────────────────────────────────────┼────────────────────────────────────┤
  │ Use                       │ graph.with_nested(parent, field, child, …)            │ graph.with_obj(child, …)           │
  ├───────────────────────────┼───────────────────────────────────────────────────────┼────────────────────────────────────┤
  │ Typical types             │ Container, Project, eventually DailyComposition       │ EqDailyEtf → EqDailyRx → DailyEMA  │
  │                           │ building its refs                                     │ chains                             │
  └───────────────────────────┴───────────────────────────────────────────────────────┴────────────────────────────────────┘
  
  Both produce a child id from "parent + slot/role," both write to the same Graph.objects frozendict. The difference is whether 
  the parent has a list to append to. That's a property of the parent type, not of the mechanism. So:

  - Container ceases to be a special type — it's just an Object with a members: tuple[Ref, ...] = () field.
  - Project ceases to be a special type — it's just an Object with storage: ... and a members: tuple[Ref, ...] = () field if you
   want it to hold things.
  - Collection disappears entirely — alias/tag/info ride on with_obj/with_nested, the registry is the graph.

  Where the "field" abstraction loosens things up

  A surprising consequence: a single object can be a parent in both senses simultaneously. A DailyComposition can be:

  - identity-derived (its id is <parent>-comp-<method>-<refs-encoded>) — built complete
  - a parent for children via its outputs: tuple[Ref, ...] field — derivs added incrementally as the handler discovers them

  Today this is awkward — DailyAggregateDeriv.new(parent_agg, key=..., index=...) is constructed inside the handler and forced
  into the graph with context.get().with_obj(child, force=True). With the generalised primitive, the handler returns (snap, 
  [(field, child)]) and the engine calls graph.with_nested(self_obj, field, child) for each. The fan-out pattern stops being an
  escape hatch and becomes the normal mechanism.

  What "identity by reference" buys us

  You called this out, but worth being explicit because it's the load-bearing invariant:

  The parent's members (or outputs, or refs) tuple holds id strings, not embedded Object copies. When a member's content updates
   (a new ValueUpdate event), the parent's tuple is unchanged. So:

  - No ObjectChange event fires on the parent when a member's value updates.
  - No re-sync of the parent or its consumers is triggered by member content changes.
  - The dependency graph (Graph.triggers) is wholly orthogonal to the membership lists. Triggers say "when member M emits a
  ValueUpdate, call handler H on container C." Containers wire that via their own depends() returning one Dependency per member
  id.
  - The only time membership changes propagate is when with_nested actually mutates the parent's field — at which point
  Graph.with_obj(parent, force=True) re-evaluates parent.depends() and re-indexes triggers. That's a build-time concern, not a
  sync-time concern.

  This is already approximately how things work (alias_parents flattens Object refs to ids on insert), but stating it as a
  design invariant matters: it's the reason with_nested is safe and cheap, and why you don't need any "I added a new sibling,
  please recompute the parent" cascade.
  
  What still needs per-type knowledge

  Three things don't get eliminated by the generalisation, just made uniform:
  
  1. Field name choice on the parent. Container calls its slot members (or objects). Project might also have members. A
  DailyComposition calls its slot outputs. These are class-level choices — the caller of with_nested has to know the field name,
   or the parent has to declare a default. I'd suggest: a Namespace.DEFAULT_SLOT: ClassVar[str] = "members" so
  graph.with_nested(parent, child) (no field arg) uses the parent's default. Override on subclasses if needed.
  2. Id-suffix encoding for slot. For tuples, slot is the index ("3"). For dicts, slot is the key ("rx"). For the agg/comb case
  the current code encodes "agg-3-4-5-span" — both the slot tag and the slot index. Two natural conventions:
    - f"{field}-{slot}" — explicit
    - f"{slot}" if field is the default slot, otherwise f"{field}-{slot}" — terser, follows your existing parent.extend_id("rx")
   convention which doesn't include a field name.

  I lean toward the second — keeps existing ids stable when a slot is implicit.
  3. Identity-derived encode_params. Unchanged — DailyEMParams.build_id still encodes span/alpha/ann/cum into the suffix per
  type. The with_nested primitive doesn't apply to these objects; their .new() factory does the encoding, and they go in via
  plain with_obj.

  Where the design lands

  Object
  ├── id: str
  ├── parent: Ref | str | None
  └── @classmethod auto_id(parent, **fields)
         # default: parent.extend_id(cls.role(**fields) + cls.encode_params(**fields))
         # identity-derived types use this from their .new() factory

  # any Object can have one or more slot fields:
  #   members: tuple[Ref, ...] = ()    — positional
  #   outputs: frozendict[str, Ref]    — named
  # slot fields are pure data; they hold id strings (Refs), not Object instances.

  Graph
  ├── objects, depends, triggers           — persisted scheduler state
  ├── aliases, tags, info                   — session-local metadata
  ├── with_obj(obj, *, alias, tag, info) -> (Graph, Ref)
  └── with_nested(parent, field, child, *, index|key, alias, tag, info) -> (Graph, Ref)
         # 1. derives child.id from parent.id + slot
         # 2. mutates parent's slot field to include child.id
         # 3. writes both to graph; re-runs parent.depends()

  Container, Project, Collection — all gone as distinct types. The thing that remains is the convention that some Objects have 
  slot fields. That convention is enforced by what subclasses you define, not by a separate type hierarchy. You could even
  imagine:
  
  - EqDailyEtf could gain a derivs: frozendict[str, Ref] slot if you wanted to attach EMA/MA chains explicitly to it — and
  with_nested(etf, "derivs", DailyEMA.new(parent=etf, span=4), key="ema-4") would Just Work. The relationship is currently
  expressed only backward (the EMA has the etf as parent); making it bidirectional via a slot is optional, opt-in, and uses the
  same primitive.

  That's the real win: you stop having three machineries (Graph registration, Collection registration, Container interning) and
  one machinery with two call sites (with_obj for backward-reference-only objects, with_nested for forward-reference cases).
  Per-type code only has to know its fields and conventions.
  
  Two specific questions before drafting code

  1. Default slot field name — members, children, objects? I'd pick members (matches "namespace member" intuition; children
  clashes with parent-relation semantics; objects is already used elsewhere for the Graph's whole-set frozendict). Worth
  deciding because it'll show up in dozens of places.
  2. Slot-derived id format — parent.id + "-" + slot (matches current extend_id("rx") style) or parent.id + "-" + field + "-" + 
  slot (more explicit, future-proofs against ambiguity)? I'd default to the first but allow overriding on a per-class basis via
  a slot_id(field, slot) classmethod. That way existing ids stay stable and unusual cases can disambiguate.
